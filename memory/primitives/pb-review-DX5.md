## Verdict: **needs-fix**

**0 HIGH.** I looked hard for one and did not find one, and I am saying that plainly rather than
manufacturing a finding: the primitive is CR-correct at every point I could reach. The
`Some`/`None` split maps exactly onto CR 611.2c vs CR 611.3a; the membership-only read is right
because `move_object_to_zone` and `add_object` are the only two id-assigning paths and both mint
a fresh `ObjectId` unconditionally (CR 400.7), so a locked id cannot survive a zone change and be
read in the wrong zone; the CR 702.26e/f guard is correctly placed *above* the membership return
and CR 702.26f's "may expire while phased out … if so they will no longer affect that permanent"
is exactly the resume-on-phase-in behaviour T8 pins; the `CreateEmblem` `None` is right (the
effect is generated by the emblem's own static ability, CR 611.3a/611.3b, not by the resolution
that created the emblem — an Elspeth emblem must keep anthem-ing later creatures, and it does);
`is_effect_active` is correctly left alone (it has no `object_id`, so a per-object set is not
expressible there, and CR 611.2b's "does nothing" is an outcome, not non-existence); and the
premise that *every* `LayerModification` variant modifies characteristics or is `SetController` —
which is what makes the lock unconditional and removes CR 611.2c's rules-modifying carve-out — I
re-derived independently over all 32 variants and it holds.

**Six MEDIUM and six LOW.** Every MEDIUM is the same shape and it is this suite's signature
failure: **a claim recorded as measured that was reasoned to.** The largest is Finding 1 — the
batch fixes a second, much bigger pre-existing defect than the one it set out to fix and does not
know it. Finding 2 is a false "verified" claim now sitting in engine source. Finding 3 is a stale
in-source note declaring, as a live limitation, the exact seed this batch closed. Findings 4–6 are
smaller instances of the same thing, including a +1 arithmetic slip in the durable record (the
suite's third such slip in three batches, and the one the dispatch brief invited me to hunt).
None of the twelve changes engine behaviour; all twelve are record, coverage or hygiene defects.

## Finding Details

### Finding 1 — The batch closes a second, much larger CR 611.2c-adjacent defect and records it nowhere

**Severity**: MEDIUM
**Files**: `crates/engine/src/rules/layers.rs::effect_applies_to` (the `CreaturesYouControl`,
`OtherCreaturesYouControl*`, `Attached{Creature,Land,Permanent}` and all `*YouControl*` arms);
`crates/engine/src/rules/resolution.rs`, `StackObjectKind::Spell` resolution tail
**CR**: 611.2a ("lasts as long as stated … If no duration is stated, it lasts until the end of the game"), 400.7

**Issue.** Every source-relative filter arm in `effect_applies_to` is written as

```rust
if let Some(source_id) = effect.source {
    let source_controller = state.objects.get(&source_id).map(|src| src.controller);
    let obj_controller    = state.objects.get(&object_id).map(|obj| obj.controller);
    source_controller.is_some() && source_controller == obj_controller
} else { false }
```

— i.e. it returns `false` for every object if the **source object no longer exists**. For a
resolution-generated effect created by an instant or sorcery, `ctx.source` is the spell's card
object (in `ZoneId::Stack`), and `resolve_top_of_stack_inner` moves that object to the graveyard
via `state.move_object_to_zone(source_object, destination)` **after** `execute_effect` has run.
`move_object_to_zone` mints a fresh `ObjectId` unconditionally (CR 400.7), so the id the effect
carries is retired the instant the spell finishes resolving.

Consequence, pre-PB-DX5: **`Triumph of the Hordes`, `Unbreakable Formation`, `Goblin Surprise`,
`Goblin War Party` mode 1, `You See a Pair of Goblins` mode 0, `Return of the Wildspeaker`,
`Finale of Devastation`'s X≥10 clause, `Crippling Fear`, `Eyeblight Massacre`, `Olivia's Wrath`
and every other source-relative mass pump/debuff printed on an instant or sorcery applied to
nobody at all after the spell resolved.** Not "the newcomer wrongly got it" — nobody got it. The
same mechanism applies to an activated ability whose source later leaves the battlefield (Mirror
Entity dying mid-turn used to undo its own pump, contrary to CR 611.2a).

PB-DX5 fixes this, silently, because `snapshot_affected_set` runs **during** resolution while the
spell object is still in `state.objects`, and the read site thereafter answers by membership and
never re-consults the source.

**This is not inference.** The mechanism is traceable in three lines of source (above), and it is
also the *only* way the batch's own **T12** can discriminate. The dispatch brief reports T12 among
the 7 probes that fail when the membership read is disabled; T12 creates no creature after
resolution and changes no controller, so its `assert_eq!(power(&state, bear_a), Some(3))` can only
fail pre-fix because the spell left the stack and the live `CreaturesYouControl` filter stopped
matching. The batch observed this failure and did not ask why.

Why it matters beyond bookkeeping: the batch's framing ("0 flips, pure correctness fix; 29
already-`Complete` defs stop over-applying to newcomers") materially understates its blast radius
in the *opposite* direction, which changes the risk calculus for the golden corpus, the benchmark
baselines, and any downstream batch that reads this record. It is also the single most useful
thing PB-DX5 did.

**Fix.**
1. Add a paragraph to `memory/primitive-wip.md`'s result summary and to the `- 70:` row in
   `crates/engine/src/state/hash.rs` recording the second closure, with the two source symbols.
2. Add the observation to T12's doc comment in `pb_dx5_affected_set_snapshot.rs` — it is currently
   labelled only as a PB-DP9 determinism check, when it is in fact the batch's only probe that a
   mass pump survives its spell leaving the stack.
3. File it as a seed row (or fold it into a new OOS-DX5-7) recording that the *pre-fix* class was
   silently wrong and that no repo test covered it, because every existing probe of this shape
   calls `execute_effect` directly with a battlefield permanent as `ctx.source` — the pattern that
   masked it (`pb_ac3_dynamic_pt_counts.rs`, and this batch's own T1/T2/T3/T5/T7/T9/T10).
4. Consider whether the residual — a source-relative filter that answers `false` when the source is
   gone — is still reachable for *static* (`None`) effects and for a sacrifice-cost activated
   ability whose source is gone before resolution (`mardu_ascendancy`'s `SacrificeSelf` +
   `CreaturesYouControl` produces an **empty locked set**, so its +0/+3 does nothing; `partial`
   already, but the reason is not the one its note gives).

### Finding 2 — The full-vs-partial-`chars` check is mis-scoped, and "verified: none exist in the roster" is false

**Severity**: MEDIUM
**Files**: `crates/engine/src/rules/layers.rs::snapshot_affected_set` (doc block);
`docs/audits/decision-point-audit.md` §8.1, row **OOS-DX5-6**
**CR**: 611.2c, 613.1, 613.7

**Issue.** `snapshot_affected_set` calls `calculate_characteristics`, which returns **fully**
layer-resolved characteristics. The live path evaluates the same predicate mid-loop with `chars`
resolved only through the layers *before* the current one — and, crucially, `calculate_characteristics`
gathers **all** effects for layer *L* before applying **any** of them, so at Layer 4 the `chars`
handed to `effect_applies_to` carry *no* Layer-4 modification at all, earlier- or
later-timestamped.

The shipped doc block and OOS-DX5-6 both say the divergence "can only diverge for a
resolution-generated effect in Layer <= 4 whose filter reads a type a **later-timestamped** Layer-4
effect changes — none exist in the roster (verified: `pb_dx5_continuous_effect_roster` step 7.4)",
and OOS-DX5-6 elaborates: *"no mass-filter def in the 38-member roster writes `CardType::Creature`
via `AddCardTypes`/`SetTypeLine`."*

Both halves are wrong:

- **The timestamp qualifier is wrong** — at Layer 4 the live gather sees zero Layer-4 effects, so
  any Layer-4 type change diverges, not merely a later-timestamped one. (Symmetrically, a Layer-5
  effect with a colour filter diverges against any Layer-5 colour change.)
- **The population checked is the wrong one.** The question is not "which *mass-filter* defs write
  `CardType::Creature` at Layer ≤ 4" — it is "which *effects of any filter* write it". Checked
  against the corpus: `crates/card-defs/src/defs/inkmoth_nexus.rs` registers an
  `EffectLayer::TypeChange` + `LayerModification::AddCardTypes([Artifact, Creature])` +
  `EffectFilter::Source` effect through `Effect::ApplyContinuousEffect`. `blinkmoth_nexus`,
  `creeping_tar_pit`, `den_of_the_bugbear` and the rest of the creature-land family do the same.

**Concrete scenario.** Animate Inkmoth Nexus, then activate `mirror_entity` (`Complete`) for {X}.
Mirror Entity's second effect is `EffectLayer::TypeChange` + `AddAllCreatureTypes` +
`CreaturesYouControl`. Pre-fix, gathered at Layer 4 against pre-Layer-4 `chars`, the Nexus is a
Land only and is **not** matched — so it got X/X (Layer 7b, where the type is settled) but not the
creature types. Post-fix, the snapshot uses fully-resolved `chars`, the Nexus **is** a creature,
and it gets both.

**The post-fix answer is CR-correct** (CR 611.2c: the set is determined from the state as it stands
when the effect begins, i.e. with all continuous effects applied), so this is not a wrongness
finding. It is a false "verified" claim shipped inside engine source and inside a seed row, on
exactly the question the plan flagged as its subtlest, plus a real untested behaviour change.

**Fix.**
1. Rewrite the `snapshot_affected_set` doc paragraph: drop "later-timestamped", state that a
   Layer-*L* effect's live filter sees `chars` with **no** Layer-*L* modification applied, and
   restate the corpus check as "which effects write the filtered characteristic at Layer ≤ 4".
2. Rewrite OOS-DX5-6 as an **open, checked finding** rather than a non-finding: name
   `mirror_entity` as the one Layer-4 mass-filter def and the creature-land family as the reachable
   counterparty, and state that PB-DX5 changes the outcome in the CR-correct direction.
3. Add a probe to `pb_dx5_affected_set_snapshot.rs`: animate a land (a Layer-4 `AddCardTypes`
   `SingleObject` effect), resolve Mirror Entity's two effects, and assert the animated land is in
   the locked set and carries every creature type. Record whether it fails pre-fix.

### Finding 4 — OOS-DX5-1's "verified by reading every `filter:` line in the file" is false

**Severity**: MEDIUM
**Files**: `docs/audits/decision-point-audit.md` §8.1 row **OOS-DX5-1**;
`crates/engine/src/rules/layers.rs::snapshot_affected_set` (doc block)
**CR**: 611.3a

**Issue.** OOS-DX5-1 states that `rules/resolution.rs`'s 13 sites are *"keyword-trigger grants
(bushido, rampage, flanking, enlist, soulbond, bloodrush, backup, token P/T overrides — **all
verified by reading every `filter:` line in the file**) … all build a `ContinuousEffect` directly
with `affected_set: None` and a `SingleObject` filter, so locking is a provable no-op for all 15
today."* The `snapshot_affected_set` doc block repeats "`rules/resolution.rs`'s 13 keyword-trigger
grants".

There are indeed exactly 13 sites, but the thirteenth is in the `StackObjectKind::ClassLevelAbility`
arm (CR 716.2a level-up), and it reads:

```rust
filter: continuous_effect.filter.clone(),
```

— an arbitrary filter taken straight from an `AbilityDefinition::Static` in the Class's card
definition. It is neither a keyword-trigger grant nor a `SingleObject` site.

The behaviour is **correct**: a Class level ability's `Static` continuous effect is generated by a
static ability, so CR 611.3a says it is not locked in and `None` is the answer, not a default. But
the seed's *reason* ("harmless because SingleObject") is wrong, and its forward-looking warning
("a mass filter landing there would be a silent CR 611.2c hole") is wrong for this site — a mass
filter there would be **correct**, and it is already permitted. (Exposure today is nil: the corpus
has exactly one `AbilityDefinition::ClassLevel` def, `druid_class.rs`, and its level arms register
no `Static` continuous effect.)

**Fix.** Split the ClassLevel site out of OOS-DX5-1; describe it as a static registration under
CR 611.3a; correct the "all 15 are `SingleObject`" and "13 keyword-trigger grants" phrasings in
both the seed row and the `snapshot_affected_set` doc block. Cite by symbol
(`StackObjectKind::ClassLevelAbility`), not line.

### Finding 5 — Three *read* sites ignore `affected_set` and OOS-DX5-1 does not cover them

**Severity**: MEDIUM
**Files**: `crates/engine/src/rules/copy.rs::copy_effect_applies_to`;
`crates/engine/src/rules/layers.rs::recompute_object_controller`;
`crates/engine/src/rules/layers.rs::expire_while_you_control_source_effects`
**CR**: 611.2c ("modifies the characteristics **or changes the controller** of any objects")

**Issue.** OOS-DX5-1 is scoped entirely to *creation* sites. But `affected_set` is a two-ended
contract, and three production sites read a `ContinuousEffect`'s membership **without** consulting
it:

- `copy_effect_applies_to` matches `EffectFilter::SingleObject(id) => *id == object_id` with a
  `_ => false` arm. A Layer-1 copy effect created through `Effect::ApplyContinuousEffect` with any
  other filter would be silently ignored, locked or not. Measured: **zero** occurrences of
  `EffectLayer::Copy` in `crates/card-defs/src/defs`, so no exposure today. (The plan's §7 asked
  step 8 to check exactly this; the check appears not to have been recorded either way.)
- `recompute_object_controller` matches `e.filter == EffectFilter::SingleObject(object_id)`. This
  is CR 611.2c's *controller* half — the one the rule names explicitly — and it is filter-based,
  not set-based. Measured: **zero** occurrences of `LayerModification::SetController` in
  `crates/card-defs/src/defs` (the sole mention, `captivating_vampire.rs`, is a TODO comment), and
  the only engine producers (`Effect::GainControl`, `Effect::ExchangeControl`) always build
  `SingleObject`. No exposure today.
- `expire_while_you_control_source_effects` reverts control only for `SingleObject` filters; its
  own in-source note already flags this as a LOW.

**Fix.** Widen OOS-DX5-1 (or file a sibling seed) to name these three *read* sites alongside the
creation sites, with the two "measured zero" figures as evidence rather than as an assumption, and
state that `affected_set` is the ready-made answer for the resolution-generated case at all three.

### Finding 8 — A vacuous `debug_assert!` in the creation site

**Severity**: LOW

```rust
eff.affected_set = Some(crate::rules::layers::snapshot_affected_set(state, &eff));
debug_assert!(eff.affected_set.is_some());
state.continuous_effects.push_back(eff);
```

The assertion is on the line immediately after the assignment and cannot fail under any edit that
compiles. It carries the plan's original wording forward without asking whether it still asserts
anything. A batch whose review standard is "an assertion that passes whether or not the bug fired
is a defect" should not ship one, however cheap.

**Fix.** Delete it, or replace it with one that can fail — e.g. after the push, assert
`state.continuous_effects.back().and_then(|e| e.affected_set.as_ref()).is_some()`, which at least
pins that the *pushed* value carries the set and would catch a future refactor that rebuilds `eff`
between snapshot and push.

## Things I checked hard and found no finding

Recorded because a reviewer's silence on these would be indistinguishable from not having looked.

1. **Membership-alone at the read site is safe against zone changes.** `state/mod.rs` has exactly
   two id-assigning paths — `move_object_to_zone` and `add_object` — and both call
   `next_object_id()` unconditionally; a repo-wide grep for direct `obj.zone = …` mutation finds
   exactly one hit, inside `add_object` itself, on a freshly-minted object. So an object cannot
   change zones and keep its id, and `next_object_id` is monotonic, so a locked id cannot be
   re-issued. Phasing (CR 702.26d), transform, turn-face-up, meld components and
   `Zone::reposition_within` (PB-DP9) are all either non-zone-changes or already mint new ids.
   `lki_objects` is a separate map that `effect_applies_to` never reaches. **No path exists by
   which a locked id survives into the wrong zone.** T9 pins the mechanism.
2. **The CR 702.26e/f guard placement is right, and the `SingleObject` exemption is correctly
   filed rather than silently kept.** CR 702.26b makes a phased-out permanent unaffectable while
   out; CR 702.26f's "may expire while phased out — *if so*, they will no longer affect that
   permanent once it's phased in" entails that a *non*-expired effect resumes. Guard-above-membership
   produces exactly that (T8), and running the same predicate at determination gives CR 702.26e's
   permanent exclusion for free (T7). The `SingleObject` carve-out genuinely has no basis in CR
   702.26e's second sentence and is genuinely pre-existing; OOS-DX5-4 states it accurately.
3. **Ordering at the creation site is CR-correct and unrecursive.** `snapshot_affected_set` runs
   after `resolved_filter` / `resolved_modification` / `resolved_duration` are computed and before
   `push_back`, so `calculate_characteristics` iterates a `continuous_effects` that does not
   contain the effect being created. That is also the CR 611.2c input: the board as it stands when
   the effect begins.
4. **Ordering *within a resolution* — the case I most expected to find a bug in — is clean.** A def
   that applies a mass pump *before* creating a token would now leave the token out of the locked
   set. I checked every roster member that both creates permanents and applies a mass filter:
   `goblin_war_party` (modes, tokens first — and MCP ruling 2019-06-14 #2 is explicit: *"If Goblin
   War Party is entwined, its modes are performed in order. The Goblin tokens you create get +1/+1
   and gain haste"*), `finale_of_devastation` (search-to-battlefield first, then the X≥10 pump),
   `elspeth_storm_slayer` 0 (counters first, then the flying grant — and "Those creatures" is
   exactly the locked set), `goblin_surprise` / `you_see_a_pair_of_goblins` / `felidar_retreat`
   (all `max_modes: 1`, so the two halves never co-resolve), `mardu_ascendancy` (two independent
   abilities). **No def orders a mass `ApplyContinuousEffect` ahead of a permanent-creating effect
   in the same resolution.**
5. **`CreateEmblem` is right.** CR 611.3a/611.3b: the resolution creates the emblem; the continuous
   effect is generated by the emblem's own static ability while it is in the appropriate zone. An
   Elspeth-style emblem must keep anthem-ing later creatures, and `affected_set: None` is what does
   that. `crates/engine/tests/core/emblem_tests.rs` exists and uses `CreaturesYouControl`, so this
   is not merely argued.
6. **The 180-site backfill.** I read every `affected_set: None` site in `crates/engine/src`:
   `rules/resolution.rs` ×13 (12 `SingleObject` keyword-trigger/token grants + the ClassLevel
   static of Finding 4), `rules/replacement.rs` ×3 (`register_static_continuous_effects` and two
   CDA registrations — all CR 611.3a statics), `effects/mod.rs` ×5 non-creation (two token P/T
   overrides, `GainControl`, `ExchangeControl`, the emblem loop), `rules/copy.rs` ×1
   (`SingleObject(copier_id)`), `rules/layers.rs` ×2 (`#[cfg(test)]`). Every one is a static
   registration or a `SingleObject` filter. `None` is the answer at all of them, not a default.
7. **The premise that makes the lock unconditional.** I read all 32 `LayerModification` variants:
   `CopyOf`, `SetController`, and 30 characteristic modifications. There is no rules-modifying
   variant, so CR 611.2c's second sentence needs no exemption arm. (Rules-modifying continuous
   effects live in `GameRestriction`/`ActiveRestriction`, untouched.)
8. **`candidate_ids_for_filter` is exhaustive and correct.** 37 `EffectFilter` variants, 37
   classified, no `_` arm (so a new variant is a compile error — the SR-5 pattern). The
   graveyard/battlefield split matches `effect_applies_to`'s own zone predicates exactly, and the
   five never-stored placeholders `debug_assert!(false, …)`.
9. **The repaired test is a genuine inversion, not a weakening.**
   `pb_ac3_dynamic_pt_counts.rs::test_611_2c_new_creature_after_resolution_does_not_get_the_locked_value`
   changed `assert_eq!(chars.power, Some(3))` to `Some(1)` with a CR 611.2c citation and an
   explicitly-observed pre-fix value. Its fixture (a 1/1 in hand moved to the battlefield after a
   `SetBothDynamic{XValue=3}` on `CreaturesYouControl`) can genuinely produce both numbers — the
   PB-DX3 T1 defect (a fixture that could not have produced the number reported) does not recur
   here. No assertion anywhere in the batch was dropped or loosened.
10. **`is_effect_active` was correctly left alone**, and the two negative claims T13 pins are right:
    a non-empty set does not resurrect an expired effect, and an empty set does not deactivate a
    live one (CR 611.2b describes an outcome; an empty-set shortcut would break the expiry and
    control-reversion bookkeeping in `expire_end_of_turn_effects` /
    `expire_until_next_turn_effects`, both of which still read `effect.filter` and still work
    verbatim).
11. **Fingerprints.** `HASH_SCHEMA_VERSION = 70`; `HASH_SCHEMA_HISTORY` has an appended
    `version: 70` row with both digests and a history paragraph that states the `loop_detection.rs`
    inclusion argument explicitly (fixed at creation, never mutated, and `id`/`timestamp` already
    distinguish a re-created effect) rather than inheriting PB-DP9's opposite call silently.
    `impl HashInto for ContinuousEffect` feeds `affected_set` after `condition`.
    `canonical_fixture` carries `Some(OrdSet::unit(ObjectId(1)))` on purpose, so the new feed's own
    bytes are inside `stream_fingerprint` — the gap several prior rows had to admit. A repo-wide
    multiline grep for `HASH_SCHEMA_VERSION,\s*69` returns only the two occurrences inside
    `pb-plan-DX5.md`'s own instructions. `ContinuousEffect` is genuinely outside the SR-8 wire
    closure and PROTOCOL is correctly unmoved at 32.
12. **`Effect::ApplyContinuousEffect` still substitutes the dynamic modifications before the
    snapshot** (`ModifyBothDynamic`/`ModifyPowerDynamic`/`ModifyToughnessDynamic`/`SetBothDynamic`
    → concrete values), so CR 611.2d and CR 611.2c are locked at the same moment and T2's X=3
    arithmetic is real.
13. **No `.unwrap()`/`expect()` added to library code.** `snapshot_affected_set` uses
    `state.expect_object` (`Option`, with a documented SR-25 justification) and
    `expect_characteristics`; the creation site uses `debug_assert!`.
