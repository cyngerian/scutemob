## 1. CR rule text (MCP, verbatim)

**611.2c** — *"If a continuous effect generated by the resolution of a spell or ability modifies
the characteristics or changes the controller of any objects, the set of objects it affects is
determined when that continuous effect begins. After that point, the set won't change. (Note that
this works differently than a continuous effect from a static ability.) A continuous effect
generated by the resolution of a spell or ability that doesn't modify the characteristics or change
the controller of any objects modifies the rules of the game, so it can affect objects that weren't
affected when that continuous effect began. If a single continuous effect has parts that modify the
characteristics or changes the controller of any objects and other parts that don't, the set of
objects each part applies to is determined independently."*

**611.2a** — *"A continuous effect generated by the resolution of a spell or ability lasts as long
as stated by the spell or ability creating it (such as 'until end of turn'). If no duration is
stated, it lasts until the end of the game."*

**611.2d** — *"If a resolving spell or ability that creates a continuous effect contains a variable
such as X, the value of that variable is determined only once, on resolution. See rule 608.2h."*
(Already implemented — the `ModifyBothDynamic`/`SetBothDynamic` substitutions at the creation site.
PB-DX5 is the *set* half of the same "locked at resolution" family.)

**611.3a** — *"A continuous effect generated by a static ability isn't 'locked in'; it applies at
any given moment to whatever its text indicates."*
**611.3b** — *"The effect applies at all times that the permanent generating it is on the
battlefield or the object generating it is in the appropriate zone."*

**613.6** — *"If an effect should be applied in different layers and/or sublayers, the parts of the
effect each apply in their appropriate ones. If an effect starts to apply in one layer and/or
sublayer, it will continue to be applied to the same set of objects in each other applicable layer
and/or sublayer, even if the ability generating the effect is removed during this process."*

**702.26b** — *"…Except for rules and effects that specifically mention phased-out permanents, a
phased-out permanent is treated as though it does not exist. It can't affect or be affected by
anything else in the game…"*
**702.26e** — *"If a continuous effect generated by the resolution of a spell or ability modifies
the characteristics or changes the controller of any objects, a phased-out permanent won't be
included in the set of affected objects. This includes continuous effects that reference the
permanent specifically, unless they also specifically refer to the permanent as phased out."*
**702.26f** — *"Continuous effects that affect a phased-out permanent may expire while that
permanent is phased out. If so, they will no longer affect that permanent once it's phased in…"*

**400.7** — *"An object that moves from one zone to another becomes a new object with no memory of,
or relation to, its previous existence."* (+ exceptions 400.7a–m, none of which apply here.)

### Card rulings used as evidence (MCP)

- **Craterhoof Behemoth**, 2025-04-04: *"Craterhoof Behemoth's triggered ability affects only
  creatures you control at the time it resolves. **Creatures you begin to control later in the turn
  won't gain trample and get +X/+X.**"* — and *"The value of X is calculated only once, as
  Craterhoof Behemoth's last ability resolves."* (the 611.2d half, already correct).
- **Umezawa's Jitte**, 2005-02-01: *"If the Jitte is moved after the '+2/+2' mode is announced but
  before it resolves, the bonus is given to the creature that is equipped **when the ability
  resolves**."* — the `AttachedCreature` lock (§3, Q3).

## 2. Design — the brief's shape is adopted, with the arguments that justify it

The brief prescribes: `Option<OrdSet<ObjectId>>` on `ContinuousEffect`; `None` = "static ability,
re-evaluate live"; populate at `Effect::ApplyContinuousEffect` only; read in
`is_effect_active` / `effect_applies_to`. **Adopted, with two refinements** (both stated as
deviations, per the PB-DP9 precedent that an inherited design must be evaluated, not assumed):

1. **`is_effect_active` is NOT changed.** See §3 Q5 — it takes no `object_id`, so it cannot
   consume a per-object set. The brief names both functions; only one of them can hold this.
2. The read is **membership AND the pre-existing CR 702.26b/e phased-out guard**, not membership
   alone. See §3 Q2.

### 2.1 Alternatives considered and rejected

**(a) A new `EffectFilter::Locked { set, base }` variant instead of a field** — the PB-DX1 shape
(prefer a variant over a field to avoid ~140 construction-site edits). **Rejected**, on three counts:

- It moves **PROTOCOL** as well as HASH. `EffectFilter` *is* inside the SR-8 wire closure (reachable
  `Effect` → `ContinuousEffectDef` → `EffectFilter`; `Effect` is in `CLOSURE_MUST_CONTAIN`), whereas
  the runtime `ContinuousEffect` struct is not (§5.3). A variant buys a wire bump the field does not.
- It breaks **three existing `match effect.filter` read sites, silently**:
  `expire_end_of_turn_effects` and `expire_until_next_turn_effects` (both in `layers.rs`) pull
  `EffectFilter::SingleObject(id)` out of expiring Layer-2 `SetController` effects to revert control,
  and `copy_effect_applies_to` (`rules/copy.rs`) matches `SingleObject` with a `_ => false` arm.
  Wrapping the filter turns all three into no-ops that still compile and still pass every test that
  does not exercise control reversion. The field leaves `effect.filter` intact and all three keep
  working verbatim — that is positive evidence for the field, not merely absence of harm.
- The distinguishing argument against the PB-DX1 analogy: PB-DX1 rejected a field because `None`
  would have been a *judgement call* at 140 sites — some right, some wrong, and nothing telling you
  which. Here `affected_set: None` is **correct at every single existing construction site by
  construction**: each is either a static-ability registration (CR 611.3a — live re-evaluation is
  the rule, so `None` is not a default but the answer) or a `SingleObject` resolution effect, where
  locking to `{id}` and live id-equality are the same function. The mechanical backfill is therefore
  not a deferred decision; it is the decision.

**(b) A parallel `GameState.effect_affected_sets: OrdMap<EffectId, OrdSet<ObjectId>>`** — zero
construction-site churn (absent entry ⇒ live behaviour ⇒ every existing test unchanged). **Rejected**:
two structures that must be kept in sync across three removal sites (`expire_end_of_turn_effects`,
`expire_until_next_turn_effects`, `expire_while_you_control_source_effects`) with nothing forcing
it; the set drops out of `ContinuousEffect`'s `PartialEq` and `HashInto`; and — decisively — a
future test that constructs a resolution-generated effect directly gets live behaviour **silently**.
This project's recurring failure mode is a gate that reports success while checking nothing; a
parallel map is that shape.

**(c) Recording the set at every `ContinuousEffect` creation site, including statics.** Rejected on
CR grounds: CR 611.3a says a static ability's effect is explicitly *not* locked in. `None` is the
rule, not an optimisation.

### 2.2 What "unconditional at the creation site" means and does not mean

`Effect::ApplyContinuousEffect` is the **only** site this batch populates. §7 audits the other 26
runtime creation sites in the engine and shows each is either a genuine static (CR 611.3a) or a
`SingleObject` filter (lock is a no-op). That audit is a step, not an assumption — a mass filter
appearing at one of those sites in future would be a silent CR 611.2c hole, and §7 leaves a
`debug_assert` behind so it is not.

## 3. The ten questions, answered

### Q1 — Where and how the snapshot is computed

**Where**: in `effects/mod.rs`, inside the `Effect::ApplyContinuousEffect` arm, **after** `eff` is
fully built (so `source`, `filter` and `duration` are all resolved) and **before**
`state.continuous_effects.push_back(eff)`.

**How**: by calling the *existing* predicate, not by writing a second filter evaluator. Build `eff`
with `affected_set: None`, call a new `layers::snapshot_affected_set(&*state, &eff)`, assign the
result, then push. This is the M11-S3 "the query and the cast path cannot drift" discipline: the
snapshot and the live read are literally the same function, so a future `EffectFilter` variant
cannot mean one thing at determination and another at application.

**Which zones are scanned**: a new exhaustive helper `candidate_ids_for_filter` classifies each
`EffectFilter` variant into a candidate zone scope:

| scope | filter variants |
|---|---|
| the object itself (fast path, no scan) | `SingleObject(id)` |
| graveyards (`matches!(zone, ZoneId::Graveyard(_))`) | `AllCardsInGraveyards` |
| battlefield (`zone == ZoneId::Battlefield`) | every other stored variant — `AllCreatures`, `AllLands`, `AllNonbasicLands`, `AllEnchantments`, `AllNonAuraEnchantments`, `AllPermanents`, `ControlledBy`, `CreaturesControlledBy`, `Attached{Creature,Land,Permanent}`, the whole `*YouControl*` family, `CreaturesOpponentsControl`, `AllCreaturesWithSubtype`, `AllCreaturesExcludingSubtype`, `Attacking*`, `LandsYouControl`, `ArtifactsYouControl`, `*OfChosenType`, `*OfChosenColor` |
| empty + `debug_assert!(false, …)` — cannot reach storage | `DeclaredTarget`, `Source`, `TriggeringCreature`, `CreaturesControlledByDefendingPlayer`, `AllCreaturesExcludingChosenSubtype` (all five are substituted or `return`ed at the creation site above this point) |

**The match must be exhaustive with no `_` arm** (the SR-5 pattern): a new `EffectFilter` variant is
then a compile error until someone classifies it. T11 is the machine gate that the zone shortcut
agrees with a brute-force scan over *all* objects — the shortcut is a performance choice, and T11
makes it a checked one.

**Recursion**: `snapshot_affected_set` calls `calculate_characteristics` per candidate, which
iterates `state.continuous_effects`. The new effect is **not yet pushed**, so it cannot see itself.
No new recursion is introduced — this is the same call hundreds of engine sites already make
(`expect_characteristics`), on `&GameState`, with no mutation. Note also that this is the *right*
input per CR 611.2c: the set is determined by the board as it stands when the effect begins, i.e.
with all *pre-existing* effects applied and this one not yet applying.

**One deliberate consequence, stated so the review can rule on it**: `calculate_characteristics`
returns **fully** layer-resolved characteristics, whereas the live path calls `effect_applies_to`
with `chars` resolved only through the layers *before* the current one. For every filter in the
corpus these agree, because types/supertypes/subtypes settle in Layer 4 and colours in Layer 5,
while every resolution-generated mass effect in the roster lands in Layer 6 or 7. They could diverge
only for a resolution-generated effect **in Layer 4 or earlier** whose filter reads a type that a
*later-timestamped* Layer 4 effect changes. **Step 7.4 requires the runner to check whether any
roster def creates a Layer ≤ 4 effect with a mass filter**; if one exists, name it in the plan
delta and add a probe. Full resolution is the CR-correct input either way (611.2c determines the
set once, from the state at that moment), so the fix is to keep it and document, not to reproduce
the partial-resolution quirk.

**Cost**: the `SingleObject` fast path means the scan runs **only** for the 37 mass-filter defs, and
**once per resolution**, not once per layer pass. Budget: ≤ (battlefield size) ×
`calculate_characteristics`. §10 requires a measured before/after on `full_turn_4p`.

### Q2 — How the read site consumes it

In `effect_applies_to`, **after** the existing CR 702.26e phased-out guard and **before** the
`match &effect.filter`:

```rust
// CR 611.2c: a continuous effect generated by the resolution of a spell or
// ability affects a set of objects determined when the effect began; after that
// point the set does not change. `Some` therefore answers this question by
// membership alone -- deliberately ignoring `chars`, `obj_zone` and the live
// filter, all of which are exactly the things CR 611.2c says must not be
// re-consulted. `None` means a static ability (CR 611.3a), which is NOT locked
// in and falls through to the live filter below.
if let Some(ref affected) = effect.affected_set {
    return affected.contains(&object_id);
}
```

**The answer is membership, plus the phased-out guard, and nothing else.** The four questions the
brief asks to be settled:

- **Not** "membership AND the live filter" — that would re-introduce the bug in the shrinking
  direction (an affected creature that stops being a creature would lose the effect, contrary to
  611.2c).
- **Zone changes need no special handling** (CR 400.7): both `move_object_to_zone` helpers mint a
  fresh `ObjectId` unconditionally, so an object that leaves and returns is a different id and drops
  out of the locked set automatically. T9 pins this rather than asserting it.
- **The phased-out guard must stay, and must stay above the membership return.** CR 702.26b says a
  phased-out permanent can't be affected by anything while it is out, and CR 702.26f says an effect
  that has not expired resumes applying when it phases in. Keeping the live guard produces exactly
  that. CR 702.26e's other half — exclusion at *determination* time — comes for free, because
  `snapshot_affected_set` runs the same predicate and the guard rejects a phased-out candidate then
  too. T7 and T8 pin the two directions.
- **The guard's `SingleObject` exemption must keep reading `effect.filter`, not the snapshot.** That
  is what preserves byte-identical behaviour for the 79 `SingleObject`/`DeclaredTarget`/`Source`/
  `TriggeringCreature`-derived defs (Q6 of the brief's "behaviourally identical" prediction). Note
  the exemption is a *pre-existing deviation* from CR 702.26e's second sentence; PB-DX5 neither
  fixes nor worsens it — filed as **OOS-DX5-4**.

**Bonus, worth stating in the source comment**: because the locked answer is layer-independent, this
also makes resolution-generated effects satisfy **CR 613.6** ("it will continue to be applied to the
same set of objects in each other applicable layer") for free. Static effects still re-evaluate
per layer inside a single `calculate_characteristics` call — a residual, filed as **OOS-DX5-2**.

### Q3 — `AttachedCreature` (Umezawa's Jitte)

**Lock it.** CR 611.2c is not qualified by filter kind, and the Jitte ruling is explicit: the +2/+2
goes to the creature equipped **when the ability resolves**. Moving the Equipment afterwards must not
move the bonus, and must not grant it to the new host. That is precisely what a locked
`{creature_A}` produces and precisely what today's `AttachedCreature` arm (which re-reads
`source.attached_to` every calculation) gets wrong in both directions. T5 is the probe.

`umezawas_jitte` is the roster's only `AttachedCreature` member reached through
`Effect::ApplyContinuousEffect`, and it is `Complete`. Equipment **static** abilities (Lightning
Greaves and friends) reach `ContinuousEffect` through `register_static_continuous_effects`, get
`affected_set: None`, and correctly keep following the Equipment around (CR 611.3a) — the two paths
are already separated by the creation site, so no filter-level special-casing is needed.

Related but **out of scope**: Jitte ruling #5 (if the Jitte leaves the battlefield *before*
resolution, the bonus goes to the most recently equipped creature — an LKI read) is unimplemented
today and stays unimplemented. Filed as **OOS-DX5-3**. Locking does not make it worse: pre-fix the
effect applied to nobody, post-fix the locked set is empty. Say so in the test module rather than
letting a `Complete` marker cover it silently.

### Q4 — Durations that are not a fixed window

**CR 611.2c still locks.** The rule's antecedent is *"generated by the resolution of a spell or
ability"* and *"modifies the characteristics or changes the controller"*. Duration appears nowhere in
it; duration is CR 611.2a/b's subject and is orthogonal. So `Indefinite` ("no duration stated ⇒ until
the end of the game", CR 611.2a), `WhileSourceOnBattlefield` and `WhileYouControlSource` resolution
effects all lock exactly like `UntilEndOfTurn` ones.

This **is** a visible behaviour change for permanent resolution effects (an `Indefinite`
"creatures you control get +1/+1" from a resolved spell will stop picking up creatures that arrive
later — which is correct Magic and is why nobody prints that card without an "until end of turn").
`EffectDuration` has no `Permanent` variant; the brief's "Permanent" is `Indefinite`.

Note `WhileYouControlSource`'s doc comment in `continuous_effect.rs` already cites CR 611.2c for the
"never resumes" property, and `expire_while_you_control_source_effects` owns that termination
imperatively. PB-DX5 does not touch it; the two uses of 611.2c are complementary (one locks the
*set*, one refuses to *resume*).

### Q5 — `is_effect_active` vs `effect_applies_to`

They answer different questions and **only one of them can hold the snapshot**:

- `is_effect_active(state, effect) -> bool` — *is this effect running at all?* Duration (CR 611.2a/b)
  and `condition` (CR 604.2). **It takes no `object_id`.** A per-object set is not expressible
  there. **Unchanged by this batch**, and the runner must add a one-line doc note saying so, because
  the dispatch brief names it and the next reader will wonder.
- `effect_applies_to(state, effect, object_id, obj_zone, chars) -> bool` — *does this effect hit
  this object?* That is CR 611.2c's question. **This is the only read site changed.**
- `effect_applies_to_object` (the `pub(crate)` wrapper used by `replacement.rs`'s IG-1 Layer-6
  check) delegates to `effect_applies_to` and therefore inherits the behaviour with no edit.

One thing the snapshot must **not** do: an effect whose locked set is empty is still *active*
(CR 611.2b's "does nothing" is a statement about outcome, not about existence). Do not add an
`affected_set.is_empty() ⇒ inactive` shortcut; it would change expiry bookkeeping and control
reversion. T13 pins that the snapshot cannot resurrect an expired effect and does not deactivate a
live one.

### Q6 — The PB-DP9 abort-and-replay interaction

`resolve_top_of_stack` clones `GameState` at entry, and on suspension restores the clone **wholesale**
and re-runs the resolution from the top once the answer is banked. A snapshot computed during a
discarded run is therefore discarded with everything else and recomputed on replay.

It lands on the same set, and the argument is that `snapshot_affected_set` is a **pure function of
`(state, effect)`**:
- `state` is byte-restored by the wrapper (that is the mechanism, not a hope);
- `effect.filter`, `effect.source` and `effect.duration` are re-derived by the same code from the
  same `ctx`;
- the scan iterates `state.objects`, an `imbl::OrdMap`, in `ObjectId` order — deterministic;
- the result is an `OrdSet`, which is canonically ordered, so the stored value and its `HashInto`
  bytes are independent of insertion order.

Nothing about the snapshot breaks the replay either: it performs no IO, mutates nothing, consumes no
`timestamp_counter` and mints no `ObjectId`. **T12** is the probe — drive an
`Effect::Sequence([ApplyContinuousEffect, <a PB-DP9 choice effect>])` through
`EffectChoiceRequired` / `AnswerEffectChoice` and assert the post-answer `affected_set` equals the
set from an identical run that never suspended. (`finale_of_devastation` is a real card of this
shape — search then "creatures you control get +X/+X" — but it is `partial`; prefer a synthetic
fixture and use the card only as a bonus check.)

One genuine hazard to record rather than discover: `loop_detection.rs`'s mandatory-state fingerprint
hashes every `ContinuousEffect`, so `affected_set` joins it. PB-DP9 deliberately kept its three new
fields **out** of that fingerprint because they grow between replays and could mask a CR 726 loop.
`affected_set` is different and may be included: it is **fixed at creation and never mutated**, and
`ContinuousEffect.id` / `.timestamp` — both already in that fingerprint — increment on every effect
creation, so a mandatory loop that re-creates the effect is already distinguishable without it.
State this explicitly in the `HASH_SCHEMA_HISTORY` row; do not leave it as an unexamined inheritance.

### Change 1 — the field

**File**: `crates/card-types/src/state/continuous_effect.rs`
**Symbol**: `struct ContinuousEffect`
**Action**: add, after `condition`:

```rust
    /// CR 611.2c: the set of objects this effect affects, determined when the
    /// effect began and fixed from that moment.

    /// `Some(set)` — a continuous effect generated by the **resolution** of a
    /// spell or ability (`Effect::ApplyContinuousEffect`). `effect_applies_to`
    /// answers by membership in this set and does not re-evaluate `filter`.
    /// CR 613.6 follows: the same set applies in every layer.
    ///
    /// `None` — a continuous effect generated by a **static ability**
    /// (CR 611.3a: "isn't 'locked in'; it applies at any given moment to
    /// whatever its text indicates"). `filter` is re-evaluated live. This is the
    /// correct value at every non-resolution creation site, not a default.
    ///
    /// The value is never mutated after construction. `filter` is retained
    /// alongside it and is still read by the CR 702.26e phased-out guard and by
    /// the two Layer-2 control-reversion sweeps in `rules/layers.rs`.
    #[serde(default)]
    pub affected_set: Option<OrdSet<ObjectId>>,
```

`OrdSet` and `ObjectId` are already imported in this file. `#[serde(default)]` keeps older
serialized states deserializing (the pattern every prior field addition used).

### Change 3 — the snapshot builder

**File**: `crates/engine/src/rules/layers.rs`
**New symbols**: `pub(crate) fn snapshot_affected_set` and `fn candidate_ids_for_filter`, placed
immediately after `effect_applies_to` so they are read together.

```rust
/// CR 611.2c: compute the set of objects a resolution-generated continuous
/// effect affects, at the moment it begins.
///
/// Uses `effect_applies_to` -- the SAME predicate the layer system applies -- so
/// determination and application cannot drift. The effect must NOT yet be in
/// `state.continuous_effects` when this is called: the set is determined by the
/// board with all pre-existing effects applied and this one not yet applying,
/// and that ordering is also what keeps `calculate_characteristics` from seeing
/// the effect being created.
///
/// CR 702.26e falls out for free: `effect_applies_to`'s phased-out guard rejects
/// a phased-out candidate here, so it is excluded from the set permanently.
pub(crate) fn snapshot_affected_set(
    state: &GameState,
    effect: &ContinuousEffect,
) -> OrdSet<ObjectId> { ... }
```

Body:
1. `if let EffectFilter::SingleObject(id) = &effect.filter { return OrdSet::unit(*id); }` — the set
   *is* that object, by definition; costs nothing, scans nothing, and keeps the 79 single-object
   defs byte-identical even when the object is not on the battlefield.
2. otherwise, for each `id` in `candidate_ids_for_filter(state, &effect.filter)`: read
   `obj.zone`, call `calculate_characteristics(state, id)` (skip on `None` — CR 400.7 LKI, not an
   engine bug, so no `expect_characteristics` here), and insert if
   `effect_applies_to(state, effect, id, zone, &chars)`.

`candidate_ids_for_filter(state, filter) -> Vec<ObjectId>` — **exhaustive `match` over
`EffectFilter`, no `_` arm** — returns the ids of `state.objects` filtered by the zone scope table
in §3 Q1. Iterate `state.objects` (an `OrdMap`) so the order, and therefore any future diagnostic
output, is deterministic. The five never-stored placeholder variants return `vec![]` under a
`debug_assert!(false, "<variant> must be substituted before storage into ContinuousEffect")`,
mirroring the existing `AllCreaturesExcludingChosenSubtype` arm in `effect_applies_to`.

## 14. Risks and edge cases

- **The backfill is 200 sites.** It is compiler-enforced and each edit is one token, but a runner
  that starts hand-editing before running `cargo check` will thrash. Follow step 3's order.
- **A test asserting the bug.** The likeliest single source of confusion in the whole batch. §8.
- **The layer-input asymmetry** (§3 Q1). Real, bounded, and checked by step 7.4 — but if a Layer-4
  mass effect does exist, the divergence is a behaviour change nobody has predicted and it needs its
  own probe before the batch closes.
- **`AttachedCreature` looks like it wants to stay live.** It does not (§3 Q3), and a reviewer's
  first instinct will be that locking it is wrong. The Jitte ruling is the whole answer; quote it in
  the source comment, not just in the test.
- **The emblem path** (`Effect::CreateEmblem`) is the one place where "created during a resolution"
  and "generated by a static ability" come apart. Getting it wrong would break Elspeth-style emblems
  in the direction that is hardest to notice (they would stop pumping new creatures). Comment it.
- **Fingerprint order-of-operations** (step 15 vs 13): the fixture's `Some` value changes
  `stream_fingerprint`. The committed digest must be the one the final tree produces — re-run the
  gate last, always.
- **Loop detection** now hashes the set (§3 Q6). Argued safe; state the argument in the history row
  rather than inheriting it silently, because PB-DP9 made the opposite call for its fields and the
  next reader will ask why.
- **This is the fifth consecutive batch in this suite whose published roster was wrong before the
  batch started** (PB-DP6 3-vs-14, PB-DP8 84-vs-77, PB-DP9 74/16/8-vs-69/16/7, PB-DX4
  97-with-two-class-D, and now 9-vs-37). Trust `all_cards()`; trust the compiler; trust the gates.
  Do not trust a number in prose — including the ones in this plan.
